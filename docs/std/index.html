#Standard library

Tern ships a standard library for the programs people write most: formatting, math, time, files and processes, JSON, logging, cryptography, SQLite, and web services with TLS, PostgreSQL and Redis. This page explains how to import modules, lists what each one is for, shows which functions need no import at all, and says which modules work on which platforms.

#Importing a module

import name makes a module's functions and types available as name.thing:

import fmt
import math

fn main():
    area = math.pi() * 2.0 * 2.0
    print("area:", fmt.fixed(area, 2))
Output
area: 12.57

from name import a, b brings chosen names in so you can use them without the prefix. You can mix both forms:

import json
from fmt import thousands, pad_left
from http import Request, new_request

fn page_of(req: Request) int:
    return req.query("page").to_int(1)

fn main():
    page = page_of(new_request("GET", "/search?q=tern&page=2", ""))
    print(pad_left(thousands(page * 1500), 8, " "), json.encode([page]))
Output
   3,000 [2]

Imports go at the top level of a file, usually first. A module that is never imported costs nothing: SQLite, for example, is linked only into programs that import sqlite.

The standard library is ordinary Tern modules in the std/ directory of the compiler, so import models looks in std/ before it looks next to your program. Don't name your own modules after the standard ones. See Modules and packages for how your own modules work.

#Builtins: no import needed

Some functions are part of the language, not a module. They need no import. Your own functions may share their names; see builtin names:

print len push pop copy abs min max sqrt float int str chr
find contains starts_with ends_with replace trim upper lower split join
to_int to_float byte repeat
get remove keys values
map filter sort_by
json_quote url_decode is_null

They are documented on the builtin functions page. Like any function, they can be called with method syntax: s.upper() is upper(s), and xs.push(v) is push(&xs, v).

The same rule works for module functions whose first parameter has a module type: d.exec(sql, params) calls sqlite.exec(d, sql, params), because d is a sqlite.Db.

import sqlite

fn main():
    d = sqlite.open(":memory:")
    d.exec("CREATE TABLE notes (body TEXT)", [])
    sqlite.exec(d, "INSERT INTO notes (body) VALUES (?)", ["same call"])
    print(d.query("SELECT body FROM notes", []))
Output
[{"body": "same call"}]

#Platform availability

Most modules work everywhere Tern runs. The exceptions depend on the operating system (sockets, SQLite, OpenSSL):

ModulemacOS / LinuxiOSAndroidWebAssembly
fmt, math, random, time, json, re, log, crypto, compress, html, csv, sql, path, flag, url, toml, binary, heap, pqueue, deque, bitset, termyesyesyesyes
os, fsyesyesyesyes, inside the directories the host grants
sqliteyesyes (SQLite from the SDK)no (the NDK has no SQLite)no
migrateyesyesno (uses sqlite)no
sqlgenyesyesno (uses sqlite)no
httpyesyesyeshttp.serve no; the helpers yes
web, pg, redis, auth, sentryyesyesyesno (no sockets)
tlsyes (aws-lc, built in)yes (aws-lc, built in)yes (aws-lc, built in)no

Using sqlite or http.serve on a target that lacks it is a compile error, not a runtime surprise:

$ tern build --target wasm app.tn
app.tn:1: error: `import sqlite` is not available on wasm
1 error(s); not compiled.

On wasm, the http module's plain functions (http.text, http.match, req.query, ...) still work, so request-handling code can be shared and tested; only the server itself is missing. A wasm program can only reach the directories its host grants: tern run --target wasm grants the current directory and /tmp; with wasmtime, pass --dir. See the WebAssembly guide and iOS and Android for details.

#What is not in the standard library

There is no MySQL client yet. For those, call a C library directly (see Calling C).
